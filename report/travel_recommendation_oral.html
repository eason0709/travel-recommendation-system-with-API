1. 封面與主題

約 0:25

大家好，我們這組的期末專題是「具可解釋性的 Soft Clustering 旅遊景點推薦與決策支援系統」。

這個系統的核心想法是：不只推薦景點，也要說明使用者像哪一類旅客、模型有多確定，以及推薦理由是什麼。

講解提醒：開場保持簡短，不要在封面頁解釋演算法。
Slide 2

2. 問題背景：旅遊推薦不能只給清單

約 1:05

我們想處理的問題是：旅遊推薦不能只給一個景點清單。

因為使用者實際規劃旅遊時，通常會同時考慮很多因素，例如預算、可用時間、天氣、體力、同行情境，以及自己偏好自然、文化、美食、拍照或熱門景點。

傳統搜尋或推薦常根據熱門度、評分或關鍵字排序，但使用者不一定知道為什麼這些結果適合自己。

所以我們希望補上的資訊是：除了推薦景點之外，也提供偏好族群解釋，以及模型信心與不確定性。

講解提醒：這頁重點是建立動機：只給排名不夠，推薦結果需要可理解、可檢查。
Slide 3

3. 系統概念：輸入、判斷、推薦、解釋

約 1:00

整個系統可以分成四個步驟。

第一步，使用者輸入旅遊條件，例如預算、時間、天氣，以及對不同景點特徵的偏好。

第二步，模型判斷這個使用者比較像哪些旅遊偏好族群。

第三步，系統根據這個判斷推薦景點。

第四步，系統提供可以檢查的證據，例如 confidence、cluster probability 和 heatmap。

因此使用者最後不是只拿到「去哪裡」，而是同時拿到推薦景點、偏好族群、模型信心和解釋依據。

講解提醒：配合流程圖講四個輸出：推薦景點、偏好族群、模型信心、解釋證據。
Slide 4

4. 資料來源與系統限制

約 1:25

資料來源部分，我們在報告中使用 OpenStreetMap，也就是 OSM 的真實 POI，Point of Interest 資料。

系統透過 Overpass API 抓取地點資料，包含 POI 的 tags、座標、名稱、地址、網站等資訊。

接著系統會根據 OSM tags 判斷地點類別，例如 museum、park、cafe、historic、shop 或 tourism 相關類型。

判斷類別之後，再依照類別 profile 轉換成本專案需要的 0 到 5 分特徵，例如 cost、indoor、nature、culture、food、popularity 和 estimated time。

這裡要注意，OSM 沒有完整評分、即時人氣、票價或訂票狀態，所以 cost、popularity 和 estimated time 仍然是根據類別與 tags 推估。

講解提醒：這頁只講 OSM。不要再講模擬景點資料；使用者輸入屬於系統操作資料，不在這頁當作資料來源展開。
Slide 5

5. Cluster 怎麼來：不是憑空分類

約 1:15

接下來說明 cluster 怎麼分類出不同旅遊族群的。

流程是先有一批使用者偏好資料，模型從裡面找出常見的旅遊偏好族群。

我們使用的是 GMM，也就是 Gaussian Mixture Model。它的重點不是只輸出一個硬分類，而是輸出使用者屬於各個 cluster 的機率。

當新使用者輸入條件後，系統會判斷他比較接近哪些已經學出的 cluster，並輸出最可能的 cluster、每群 probability，以及模型 confidence。

所以 cluster-only 並不是完全沒有資料也能使用。它的價值是在已有初始資料後，輔助新使用者或互動資料不足的使用者。

講解提醒：可補充：目前 cluster 主要根據景點偏好特徵，不用預算、天氣直接定義族群。
Slide 6

6. 推薦方法：Personal、Cluster、Collaborative、Hybrid

約 1:30

我們比較了四種推薦方法，可以先用白話理解。

personal-only 是直接看這個使用者自己的偏好，找出最像這些偏好的景點。它不負責分類。

cluster-only 是先看使用者比較像哪一群人，再用那群人的平均偏好推薦。它的功能是說明使用者比較像哪一類旅客。

collaborative-only 則是看同一個 cluster 裡的其他使用者互動紀錄中，哪些景點平均評分較高，再推薦那些景點。

hybrid 是把個人偏好、cluster 偏好和互動資訊混合。

因此這四種方法的差異不只是分數高低，而是它們各自使用的資訊不同，也提供不同層次的解釋。

講解提醒：依照更新後 Slide 6。注意 collaborative-only 說成「互動紀錄」，不要說「模擬互動」。

7. Demo 1：輸入條件到 cluster probability

約 1:15

接下來進入第一段 Demo。這段的目標是展示：使用者輸入條件後，系統如何判斷他比較像哪一類旅客。

我們會輸入一組明確情境，例如天氣較差、體力偏低、室內偏好高、文化偏好高。

輸入後，畫面會顯示最可能的 cluster、cluster confidence，以及每一個 cluster 的 probability。

這裡的重點不是硬把使用者分成單一類型，而是讓觀眾看到模型同時提供分類結果與不確定性。

如果 confidence 高，代表模型判斷比較明確；如果 confidence 低，代表使用者可能同時接近多種旅遊類型，不應該只看單一 cluster label。

講解提醒：Demo 時只操作一組最穩定的情境，避免現場花太多時間調參數。
Slide 8

8. Cluster 測試參數表

約 0:45

這一頁整理的是不同偏好類型的測試參數。

我們設計了自然景點、室內文化、美食、拍照打卡、高消費、熱門景點、低消費輕旅行，以及無明顯偏好的案例。

這些測試案例的目的，是檢查模型面對不同輸入時，是否能產生合理的 cluster 判斷與 confidence。

例如自然偏好很高的輸入，理論上應該接近自然景點相關 cluster；中性輸入則不應該得到過度明確的判斷。

講解提醒：這頁不要逐欄念表格。可說明：參數表是備用測試案例，用來證明有準備不同偏好類型檢查 cluster 是否合理。
Slide 9

9. Demo 2：推薦景點與推薦理由

約 1:15

第二段 Demo 看推薦景點與推薦理由。

目前 App 展示的是 cluster-based 推薦，也就是根據使用者所屬 cluster 的平均偏好，和景點特徵比較後排序。

推薦表格裡可以看到景點名稱、景點類型、推薦分數，以及室內、文化、自然、美食、熱門程度和 estimated time 等特徵。

這裡要強調，推薦表格不是只給排名，而是讓使用者可以檢查推薦是否合理。

例如如果使用者屬於室內文化相關 cluster，推薦結果中就應該出現室內或文化特徵較高的景點。若結果明顯不合理，就代表資料轉換或 cluster 解釋需要再檢查。

講解提醒：這段可配合 App 操作或截圖。不要承諾推薦一定完美，重點是結果可檢查。
Slide 10

10. Heatmap：如何解釋 cluster

約 1:20

接著看 heatmap。heatmap 的作用是解釋每個 cluster 的特徵。

表格中的數字是標準化後的平均值，也就是 z-score。數字越高，代表這個 cluster 在該特徵越高於整體平均；數字越低，代表越低於整體平均。

我們用一個簡單規則判讀：z 大於等於 1 可以視為特高，z 小於等於 -1 可以視為特低。接近 0 的值則不要過度解讀。

例如自然景點 cluster 的 nature value 明顯高，同時 indoor、cost、culture、food 和 popularity 低，就可以解釋成自然景點型。

如果看到熱門和高消費在同一群，這通常表示在目前資料中，這兩種偏好常一起出現。GMM 只是把資料中的共同模式學出來，不是演算法硬把它們綁在一起。

講解提醒：只講 1～2 個 cluster 範例即可，不要逐列解釋整張 heatmap。
Slide 11

11. 方法比較：差異不大，但都高於 baseline

約 1:00

接著看方法比較結果。

從表格可以看到，四種方法都高於 random baseline，代表系統不是隨機推薦。

personal-only 的 mean similarity 和 recommendation lift 略高，hybrid 接近 personal-only，cluster-only 和 collaborative-only 稍低。

但這些差異其實不大，所以我們不會把結果解讀成某個方法大幅勝出。

比較合理的說法是：personal-only 適合直接個人化排序；cluster-only 和 collaborative-only 雖然分數略低，但能提供族群偏好、相似使用者參考和解釋價值。

講解提醒：不要說 personal-only 明顯最好，只說略高；重點是四種方法都高於 baseline。
Slide 12

12. 限制與結論：準確度不是唯一目標

1:20

最後是限制與結論。

第一，OSM 沒有完整評分、人氣、票價或訂票狀態，所以部分景點特徵仍然是推估值。

第二，目前 App 主要展示 cluster-based 推薦，而 personal-only、cluster-only、collaborative-only 和 hybrid 的比較是在離線評估中完成，因此 App 展示與離線評估要分開說明。

第三，未來可以加入交通時間、地理距離、即時天氣與更多互動資料，也可以使用 Precision、NDCG 和 diversity 等推薦系統指標。

總結來說，本專題的重點不是宣稱分群一定讓推薦更準，而是讓推薦系統從只輸出結果，變成可以說明使用者偏好族群、模型信心和推薦依據的決策支援工具。
